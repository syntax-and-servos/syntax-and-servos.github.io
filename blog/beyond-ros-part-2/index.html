iceoryx2: Shared Memory IPC

At the end of the last section we mentioned "shared memory", which is the key for the fast and efficient Inter Process Communication (IPC) with iceoryx2. It is a physical memory region that can be accessed by multiple processes if their virtual address space includes it. This form of communication is considered the fastest IPC method [2] and is similar to threads sharing memory, including the need for synchronization to avoid data races. After the initial shared memory setup, communication doesn't involve any system calls and also doesn't impose data (de-)serialization for types that are safe to share directly (no pointers, fixed layout), resulting in true zero-copy communication. We'll see later that real-world robotics messages are rarely of this type. Strings, variable-length arrays, and schema evolution require serialization, which is where FlatBuffers comes in, which add a small cost for writing data. Some ROS middlewares like CycloneDDS support shared memory as an opt-in feature, but several restrictions apply including that it is impossible to check whether the shared memory transfer is actually applied [3].

If you paid attention, you may have realized that all of the above is not applicable for inter-host communication. This is the domain where ROS 2 and the DDS middleware shines. Fortunately, iceoryx2 provides a Zenoh tunnel, connecting separate hosts running the iceoryx2 middleware, but more on that in another blog post.

The loan-based publish model

Instead of building your data and then copying it into the middleware, the middleware gives you a buffer, i.e. a slice of shared memory, and you write directly into it:

sequenceDiagram
    participant P as Publisher
    participant SHM as Shared Memory
    participant S as Subscriber
    P->>SHM: 1. loan() from shared memory
    SHM-->>P:  return provided slice
    P->>P: 2. write data into slice
    P->>SHM: 3. send() — ownership transfer
    SHM->>S: 4. receive() — read from same slice
    S-->>SHM: drop: slice is returned
  • The API flow: loan → write → send (transfers ownership to subscribers). See the publish-subscribe getting started guide [7] in the iceoryx2 book for the full walkthrough.

  • Emphasize: the subscriber reads from the exact memory the publisher wrote into — no copy, no deserialization

Services and discovery

  • Communication channels are called "services," identified by string names (similar to ROS topics). See the communication model [10] chapter for the full service-oriented architecture.
  • open_or_create semantics: if the service exists, join it; if not, create it
  • No need for a separate discovery protocol — the shared memory segments are named files in the filesystem

FlatBuffers: Serialization that doesn't get in the way

  • The natural question: if we're using shared memory, why do we need serialization at all?
  • Answer: shared memory alone works for fixed-size POD types, but real robotics messages have strings, variable-length arrays (point clouds, trajectories), and need to work across languages and evolve over time
graph TB
    App["Your Code"] --> FB["FlatBuffers (serialization)"]
    FB --> IOX["iceoryx2 (shared memory transport)"]
  • FlatBuffers [13] gives us: zero-copy reads (just pointer arithmetic), schema evolution (add fields without breaking subscribers), and cross-language support from the same .fbs schema. See the FlatBuffers documentation [14] for the full reference.

  • Emphasize: no deserialization step, no copy — just pointer arithmetic into the buffer
  • The same bytes work whether they came from shared memory, a network, or a file on disk

Schema evolution in one paragraph

  • Connect back to the rosbag pain point from post 1
  • FlatBuffers rule: add new fields at the end, never remove or reorder. See the evolution documentation [17] for the full rules and examples.
  • Old subscribers simply ignore new fields, new subscribers use defaults for missing fields
  • Your months-old recorded data stays readable after you add a field — no recompilation, no conversion tools
